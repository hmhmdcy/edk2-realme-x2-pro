# 加快全外设适配

2026-10-16。前摄225控制链已通过本轮验收，下一轮优先后置四摄、GNSS与蜂窝主要阻塞；真实画质、长稳和整机其它外设仍在goal内。[本轮结果](README.md)、[全清单](../../linux-port/docs/HARDWARE-STATUS.md)。

当前构建SDK为Alpine edge/aarch64，C++编译器通过ARM模拟运行，没有ccache。宿主已有aarch64-linux-gnu-gcc，但没有配套C++/musl工具链，不能把glibc交叉C编译器直接替换到Alpine C++产物。已保留对象树用于增量构建，尚未完成宿主工具链迁移，不能声称已有确定倍数收益。[环境核对](build-environment-validation.json)。

[pmbootstrap官方交叉构建文档](https://docs.nura.eco/pmbootstrap/main/cross_compiling.html)将QEMU-only列为慢、crossdirect列为中、cross-native2列为快；后者支持Meson，自3.4起可用，将构建工具放宿主侧、目标依赖放sysroot。先在隔离构建环境验证版本匹配、链接与IPA签名，再计时比较；不修改当前SDK、签名输入或回退包。该模式目前不支持内核，内核沿用其独立交叉构建流程。

执行顺序：

1. 收齐225记录和源锁，结束本阶段前摄控制测试。已有矩阵通过后只对实际改动补必要回归，避免无变化重跑整套。
2. 为后摄/GNSS/蜂窝各选一个能区分原因的最小实验，逐层检查供电、固件/校准、总线/RPC、内核与用户态服务；每次只改一个因素，记录结果与回退。
3. 同机Android正常日志与寄存器/控制读数作为对照，再比较realme/OPPO/一加对应SoC设备树和驱动；社区经验按SoC/传感器/固件版本筛选。已有[相关机型GNSS调查](../kernel205/GNSS-RELATED-DEVICES.md)，不重复已否定的时间误差试验，也不把他机NV值写入本机。
4. 用户方便时，室外开阔地GNSS对照能减少“驱动未接收”与“室内信号弱”的歧义；白天画质对照能验证颜色/几何。当前仍按室内窗边、关灯条件工作，不依赖即时人工操作。
5. 用户已授权并启动三路只读研究：GNSS、后摄、蓝牙/传感器/蜂窝。各自提交有源码依据的候选方案和最小判别实验，主流程筛选后实施；手机电源/固件/驱动修改和测试串行执行。

验收以可复现的设备功能为准：GNSS正CNR与真实fix、后摄有效RAW/正确画面、蜂窝卡检测与注册/数据分别记账。编译提速以实际耗时和相同功能产物为准；不预先承诺完成日期或倍数。
