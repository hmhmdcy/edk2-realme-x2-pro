# 464：把FULL空队列与应用归还请求对齐

只读复用461 r2原件，没有新手机、SDK或构建操作。[检查](inspect-supply.py)同时固定实际449客户端与461管线源hash，核对四请求缓冲及函数顺序；没有重新读取285张图，也没有过滤回执或重跑相机。

| native 1080p缺口 | FULL软件queued=0区间 | 其中应用仍在处理旧图 | 应用提交请求至内核QBUF上界 |
| --- | ---: | ---: | ---: |

客户端只有四个请求，由单个应用线程依次处理。源码在 `meanY()` 完成拷贝／求均值／保存、元数据检查和输出之后才reuse／queue该请求；本次日志的request序号连续，下一张图的I/O开始给出了这次提交的上界。内核QBUF分别在这一上界后1.701／0.142ms发生；这里是时间界限，不是假造的API入口时间戳。

应用首三张1080p拷贝和求均值耗时73.523／61.623／49.291ms；两处对应旧图的保存另耗4.569／13.480ms。旧SOF0／2的成功IPE回执在空队列开始前71.495／119.306ms已出现。按实际管线顺序，内部FULL先归还，随后才通知应用；应用已进入图像I/O，说明该内部归还路径已经走过。对应原FULL与下一QBUF的index也一致。

所以本次确实存在应用仍持有请求、软件队列等其归还的空窗。对应焦点评分约3.6ms、native IPA dispatch为93／99µs；没有证据要求为了这两次供给空窗修改原厂LTM／GTM数学或扩大底层缓冲数量。

## 结论边界和后续选择

[收据](supply-validation.json)保留全部数字。第二处PD10-ready用户态记录落在FULL软件空队列区间内；第一处该记录出现时FULL已重新排队。现有记录没有实际SOF边沿／硬件bank状态，不能把软件供给中断直接等同于缺SOF4当时的物理FIFO因果，也不能推广为450／452旧GStreamer缺口的同一根因。

449 lifecycle继续负责同Manager重开、完整图像／元数据和资源恢复验收；连续帧率与偶发缺口使用已有低拷贝GStreamer消费者及实际FULL事件检查。它们覆盖不同负载。后续若补旧GStreamer缺口，沿用真实FULL角色和MONOTONIC取证；本轮无需为这两处应用持有空窗重复长测或改变生产调校。多摄正常模式、原厂IQ绑定和共享资源生命周期继续推进。
