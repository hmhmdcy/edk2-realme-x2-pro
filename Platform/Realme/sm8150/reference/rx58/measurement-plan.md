# RX58：只测重开串口后的首条输出

状态：**方案已准备和模拟检查，尚未获批、没有执行。** RX57 两次单次 UAC 均已使用。
此前第二次获准抓取已完成、两项配置已恢复，不将旧授权重复使用。

依据：三个 CRC 有效快照中的真实缺帧，都恰好位于重开 Windows 串口后的首条
Ctrl-U 状态输出开头；另外 511 帧直接匹配。RX53 首次 Ctrl-U 已受理，说明启动 RX
失败不是 TX 缺口的必要条件。实装驱动对非成功 USB 读只记四字节状态，不记长度或
正文；后续 ReadIrpCompletion 也跳过正文入串口缓冲。这是可区分的候选分支，未证实根因。

这次改变的是：**在相同的启动触发点，同时取得 USB 完成事件和驱动原始字节日志**，
再和同 owner GET_STATS/raw、手机软件发送快照比较。不是重复普通 echo 的 passing 流程。

## 授权范围

- 仅一次新 UAC，管理员运行 `driver-log-etw-admin.ps1 -Mode Arm`。
- COM14 同一设备软件键的两项：QCDriverConfig=`0x80000000`，
  QCDriverLoggingDirectory=`\??\E:\edk2-samurai-out\rx58\driver-logs-first-status-01`。
  启用和恢复各重载这个 9505 叶节点一次；保留其他配置。两项须原来不存在，否则停止。
- 同一个管理员帮助进程启动 USBXHCI/UCX/USBHUB3 ETW；64 MB 环形文件留在本机。
  这些系统提供者可能包含其他 USB 设备事件，Git 仅保存本次 EUD 提取和必要元数据。
- 正常用户手动持有最多三个依次关闭的 COM14 owner。前两个只取首条 Ctrl-U 状态和
  Ctrl-P 接收计数，随后 Ctrl-] 关闭；第三个相同，再读一个冻结快照。
- 使用未改动的 RX55 诊断：首次清行至多两次 Ctrl-U；收到新回执才输入。
  第三 owner 的数据只发送一次，不重试；LEN2 继续留给 F1。
- 抓取须在 ready 后 60 秒内开始，总计不超过 180 秒。三个诊断分别上限 20/20/90 秒，
  包括等待和 finally；共同计时防止启动末个 owner 超界。管理员全程上限 300 秒含恢复。
- 不刷机、不重启手机、不安装/替换驱动、不改终端/内核/等待配置，不发额外 reset 或 F1。
- 每个串口 finally Close/Dispose；末次或失败后申请恢复。管理员 finally 停 ETW
  （最多三次有界 stop），删除原本不存在的两项、重载同节点、写清实际结果。
  原值若被第三方改动则保留并明确报冲突，不能声称恢复成功。

## 手动数据和停止条件

前两个 owner：新启动回执完整/缺口都保留，Ctrl-P 记排空计数，Ctrl-]。
第三个 owner：先 Ctrl-P；随后逐帧受理的以下两条命令只提交一次：

```text
dd if=/sys/bus/platform/devices/88e0000.serial/tx_journal of=/tmp/R58J bs=4096 count=1
base64 /tmp/R58J
```

保存 immutable 3120 字节快照并验证 CRC。排空后 Ctrl-P、Ctrl-]。任一 owner 无新
启动回执、数据无回执、身份改变、出现其他 owner 或超时，就停止后续输入并 finally 恢复。
不按缺失长度补造正文；快照若已覆盖最早窗口则明确记录观察不足。

## 判据

1. 真缺口时，ETW 非成功完成是否有可信的实际长度/数据、日志是否只记错误状态：
   支持继续查驱动拒绝分支；正长度字段本身不能冒充有效数据。
2. 日志有完整帧而计数/raw 少：查串口缓冲之前或之后的驱动/应用边界。
3. 日志、ETW 成功读都少：继续查更早 EUD/USB；这些软件工具仍测不到物理 ACK/DATA0/1。
4. 三次均通过：只记录未复现，不宣称修复，不原样再循环。

脚本语法和七种模拟失败路径、真实 Stop 函数的有界重试已检查；模拟不证明实机
ETW/PnP/调度成功。只读 Plan 会核对实装 SHA/PnP/注册表/USBIP，不打开串口。
